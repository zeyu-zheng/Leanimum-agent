# ReuF2F

ReuF2F prepares tasks and grades patches. Leanimum only launches solver environments,
runs the agent and collects predictions/trajectories, following the upstream
mini-SWE-agent batch flow. There is no benchmark exporter or Comparator grading
implementation in this repository.

## Prepare once, run independently

In the benchmark checkout, run its `reuf2f prepare-tasks /tmp/reuf2f-tasks` command.
Use the installed CLI or the Python interpreter prescribed by that checkout.
Give this runner the resulting **release directory**, not the benchmark checkout:

```bash
# Start one shared-image container per selected task.
leani-extra reuf2f --subset /tmp/reuf2f-tasks \
  --filter '^berger-modified-egz$' -m YOUR_MODEL -o /tmp/reuf2f-run

# Parallel batch with one budget per task, not one per direction.
leani-extra reuf2f --subset /tmp/reuf2f-tasks --slice 0:5 --workers 2 \
  -c reuf2f.yaml -c agent.step_limit=100 -c agent.cost_limit=5 \
  -m YOUR_MODEL -o /tmp/reuf2f-batch
```

The release has `tasks.jsonl` with `instance_id`, `source_revision`, `base_commit`,
`source_file`, `problem_statement`, and a committed workspace at `tasks/INSTANCE_ID/workspace`.
The runner reads the expected five-file baseline from that commit, ignoring
working-tree edits. It transports the source and consistency data, not replacement
TOML/toolchain/lockfile contents. After initialization:

```text
/testbed/
  berger2019modified.lean   # example: retain the original filename
  lean-toolchain
  lakefile.toml             # image configuration, only Main root replaced
  lake-manifest.json
  .gitignore
  .git/                     # fresh local repository with one initial commit
  .lake/                    # image-local dependencies/build artifacts
```

Each task retains its original filename, namespaces, definitions and theorem text.
For example, `berger2019modified.lean` has `berger2019modified.conjecture_4_2`
and the appended `berger2019modified.conjecture_4_2_neg`. The release's
`problem_statement` identifies the file and both full theorem names. Negation is
prepared and independently verified by ReuF2F, not regenerated by this runner.
One agent chooses either direction within its budget; the unchosen theorem may
remain `sorry`, but the selected proof must not depend on it, even indirectly.
The agent checks with `lake build` (the exported package has a default target),
or `lake build berger2019modified` for this example. Comparator runs separately.
No `TASK.md`, `Submission/`, second copy of the problem, benchmark checkout,
`AGENTS.md`, per-task grading controller, or fixed `ReuF2FEval` namespace is injected.
The shared image also contains generic Comparator/lean4export/Landrun tools;
agent self-checks remain separate from official grading in a fresh container.

## Shared Docker image

Defaults are `zeyuzhenghub/lean4:v4.33.0`, `linux/amd64`, and `/testbed`. The updated
image recipe still needs building and publishing; its availability is not implied
by the default tag. Regenerate task releases for Lean v4.33.0 rather than using
the old toolchain's releases.
There is no task-specific build/push. These defaults live
only in `reuf2f.yaml`; the runner does not duplicate image/platform/workdir defaults.
The benchmark command timeout is 1200 seconds. No agent wall-clock limit is set;
the existing 250-step/$3 limits and 3-hour container lifetime remain unchanged.
These are separate controls: removing the agent wall-clock limit does not remove
the container's lifetime limit.
Use `-c reuf2f.yaml -c environment.image=...` to pin a digest for a published run. Podman works through
`-c environment.executable=podman`. Keep `--platform linux/amd64` if overriding
`environment.run_args` for resource limits.

Before the first model query, the runner keeps `lakefile.toml`, `lean-toolchain`,
`lake-manifest.json` and `.lake`. It changes only `roots = ["Main"]` to the task
module in the existing TOML, adds the Lean source and `.gitignore`, checks the
expected TOML hash and exact locked dependency entries, verifies installed commits
and tracked files, and builds the named module. It checks that preflight left
those initial files unchanged, then creates a normal local Git commit. No release
commit objects or whole replacement project configs are uploaded. A mismatch fails
setup: no `lake update` or silent fallback. The image needs bash, Python, Git, Lean,
the matching TOML recipe and cached dependencies. Docker mounts no host directories,
credentials or socket by default. These are consistency checks, not a security guarantee.

No host fallback occurs if the selected container engine is missing. Apply host memory/process/disk and
network limits appropriate for untrusted solver commands. The model client runs on
the driver; provider credentials are not forwarded unless explicitly configured.
Real Docker preflight and benchmark isolated Comparator smoke are release gates;
local subprocess tests alone do not establish that either works on an evaluation host.

## Execution backend

The upstream `--environment-class` option overrides `environment.environment_class`
in config. ReuF2F supports only:

- `docker` (default): start the shared image and upload the prepared task. Podman
  uses this same class with `-c reuf2f.yaml -c environment.executable=podman`.
- `local` (explicit): execute shell commands in the driver's environment, without
  starting another container. This can be a disposable host or an outer container
  that already provides Lean. **There is no per-task security isolation.**

The prepared Lean project for local runs is selected with `environment.cwd`:

```bash
leani-extra reuf2f --subset /tmp/reuf2f-tasks --slice 0:1 \
  --environment-class local \
  -c reuf2f.yaml -c environment.cwd=/path/to/prepared-lean-project \
  -m YOUR_MODEL -o /tmp/reuf2f-local-run
```

The prepared project must have the matching image `lakefile.toml` (Project with
root Main), `lean-toolchain`, `lake-manifest.json`, installed Lean on PATH and
dependencies already checked out/cached in `.lake/packages`. On a host
using the shared image as its outer environment, `/testbed` serves this purpose.
The runner does not install or update dependencies. It copies the task into a
fresh `OUTPUT/INSTANCE_ID/workspace-*` directory, copies those configs from the
prepared environment (not the release), changes the Main root, links the prepared dependencies,
checks their revisions/tracked files, builds the task, and creates an initial Git
commit there. The prepared project's files and the release are not cleaned,
overwritten, or used as the agent's working tree. Local attempt workspaces are
retained with the run output, including on errors and retries.

Concurrent local tasks have separate source/build directories but share the linked
dependency cache and the host's resources. An agent can still read host files or
modify those shared dependencies: use a no-secret disposable environment. This is
not equivalent to separate Docker containers. Use a compatible Linux environment
or override the prompt's Linux assumptions if running locally elsewhere.

A Docker failure is never retried as local. Singularity, SWE-ReX, Modal, ConTree and
Bubblewrap are not enabled for ReuF2F; generic `leani` backends remain unchanged.
The selector is only an agent runtime setting, not part of the released task or
prediction schema, and does not change the independent Comparator evaluator.

The shared image is maintained in the ReuF2F repository's `docker/` directory,
adapting SWE-bench's directory discovery to `tags/<instance_id>/task.yaml` plus
adjacent `Dockerfile`, inside the existing checkout rather than another Git repo.
Only image recipes use `tags/`; prepared mathematical task releases still use `tasks/`. Run
`reuf2f images build ./docker` from the ReuF2F checkout. Each entry identifies a
shared Lean environment, not a mathematical item. The recipe specifies the installed
Lean/Mathlib version; `task.yaml` specifies the environment ID, image name and platform.
No version argument or build-argument injection is used.
`reuf2f images push ./docker` is a separate, explicit upload step. In Docker mode the
agent runner only starts an available image; local mode starts no image. Neither
builds or pushes images per task. See ReuF2F's `docker/README.md`.

## Predictions, retries and grading

The runner writes an ID-keyed `preds.json` in the standard three-field format:

```json
{"berger-modified-egz":{"instance_id":"berger-modified-egz","model_name_or_path":"model","model_patch":"diff --git a/berger2019modified.lean b/berger2019modified.lean\n..."}}
```

Submission follows the pinned upstream mini-SWE-agent protocol:

1. The agent edits its task file and local Lean modules under names it chooses.
   For `Support/Lemmas.lean`, add `[[lean_lib]]` with `name = "Support"` to lakefile.toml
   and `import Support.Lemmas` in the task. Keep Project's root and dependencies;
   run `lake build` to build the task and its imported dependencies.
2. It adds new helpers to Git's index (`git add -N -- PATHS`) and writes
   `git diff -- berger2019modified.lean lakefile.toml Support/Lemmas.lean > patch.txt`
   for the example above (list the actual files changed).
   As in upstream, the prompt says `Do NOT commit your changes.` It does not supply
   a fixed commit ID or try to recover changes the agent has already committed.
3. It inspects the patch, then submits with a separate command:

   ```bash
   echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT && cat patch.txt
   ```

The existing environment converts that command's output into `submission`, and the
upstream runner saves it directly as `model_patch`. There is no post-run workspace
scan, source snapshot protocol, archive, or second Git repository on the driver.
`patch.txt` is created by the agent when submitting, not a required input file.
New helpers need `git add -N`; ordinary `git diff` omits staged/committed changes.
The agent is responsible for creating and inspecting its patch. On errors/budget exits without
a submission, the prediction is empty rather than automatically salvaged from the
workspace. A nonzero submission command does not finish the task.

Generation does not validate the patch or interpret a success message as a score.
For example, submitting `accepted` literally stores that text as a patch, which the
benchmark rejects. The **original trusted release**, never the container's Git state,
is the evaluator's authority. ReuF2F checks paths, file types, sizes, statements,
axioms and proofs after replay in a fresh root grading container, using Comparator's
upstream Landrun calls. There is no additional worker-user or custom seccomp layer.
Container root is not a tamper-proof boundary between submitted code and grading
artifacts. Missing evaluation infrastructure is an error, not a host fallback.

The output contains only the upstream-style artifacts:

- `preds.json`: three-field predictions.
- `leanimum.log` and `exit_statuses_TIMESTAMP.yaml`: logs and termination status,
  including setup failures before an agent can be constructed.
- `INSTANCE_ID/INSTANCE_ID.traj.json`: messages, budgets, termination and config;
  the release `source_revision` and `base_commit` are included here as data provenance,
  not as the container's local HEAD or a diff instruction.

There are no separate `task.json` or `result.json` files. Trajectories are saved
when an agent was constructed. Model initialization failures are logged by batch
error handling and write no prediction or trajectory, as upstream; normal resume
retries these IDs. After model initialization, environment/setup failures are
recorded in the log, batch status and an empty prediction. Containers are cleaned
up even on failure. `Submitted` is
not a proof verdict. Pass `preds.json` and the original trusted release to ReuF2F's
`eval RELEASE -p preds.json --run-id RUN` on the separate prepared evaluation
host. ReuF2F saves `logs/evaluation/RUN/results.json` and per-instance reports;
repeat the same command to resume. `reuf2f report RUN` re-grades the saved process
exit evidence without running Lean or Comparator again. Use `-d RELEASE` when the
release has moved or run metadata is missing; `--repo` locates the benchmark checkout.
Repeat `-i ID` for a subset-only report. The optional predictions snapshot can be
replaced by saved per-instance patch artifacts; no input-equality checks are added
at re-grading time. Keep each run associated with the same experiment.
Full raw process streams
are saved alongside the per-instance reports. ReuF2F evaluation uses `-i/--instance` and
`-j/--workers`; this agent runner uses upstream `--filter`/`--slice`.
ReuF2F checks proof and refutation concurrently, with one shared deadline and one
point for either accepted direction. It creates separate temporary Lake projects
inside a fresh root grading container using Comparator's upstream Landrun calls;
it never reuses the solver container or runs submitted Lean on the host. `-j N` can run up to
`2N` Comparator processes. This does not increase the agent's model budget.
Invalid per-item patches and infrastructure failures are recorded without losing
other instances' results. An older release remains usable after unrelated
benchmark commits when its selected source/metadata and dependency config match.

Selection retains `--filter` (regex), `--slice`, deterministic `--shuffle`,
`--workers`, and recursively merged `-c` configs. `--subset` supplies the local
release directory; the old `--tasks`, `--problem` and `--list` interfaces are removed.
There is no `--split`: this benchmark release has no split dimension.
Use `--slice 0:N` to limit a run. The redundant `--limit` and `--image` shortcuts
are removed; image overrides use the existing config mechanism.
Without `-o/--output`, run artifacts are written to the current directory, as in
the upstream runner. Pass `-o DIRECTORY` to choose another location; no timestamp
directory is generated automatically.
Existing prediction IDs, including failed attempts, are skipped unless
`--redo-existing` is set. Output must be outside the release directory. The old
`--repo` catalog reader, `--prepare-only` generator, and archive submission path
have been removed rather than kept as a second implementation.

Regenerate older releases whose `problem_statement` still asks for a supplied
`base_commit` or fixed `Main.lean`/`ReuF2FEval` names. Records without
`source_file` are not supported. New releases contain no agent-side fixed-commit instruction;
the release's `base_commit` field remains for trusted file loading and grading.

## Testing and other workflows

ReuF2F tests exercise both actual local subprocess execution and Docker/Podman.
Docker tests skip when no engine is available; this does not select local as a
fallback. Evaluator integration tests use the same shared Lean image, rebuilt with
its fixed verifier tools on a compatible Linux Docker host. Grading follows the
upstream root-user execution model, without a separate worker-user or custom
seccomp layer. Comparator retains its own Landrun build/export calls.
There is no separate grading image: ReuF2F starts a new container from the shared
image and never reuses the solver container.
The generic `leani` CLI continues to support upstream backends for other workflows.

Legacy releases containing `lakefile.lean` must be regenerated. The evaluator
accepts TOML library layout and local Lean sources; it does not trust submitted
dependency/plugin/compiler-option overrides or build artifacts.
